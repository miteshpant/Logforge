# AI evaluation

Every AI feature must reach its target on these evaluations before it ships
([PLATFORM_ROADMAP.md](../../../docs/PLATFORM_ROADMAP.md), Phases 8–10). The
harness is provider-agnostic: a *system* is any function `item -> output`, so
a model-backed feature, a rule-based fallback, or the dataset's reference
answer are all scored the same way.

| Task | Input → output | Item score |
|---|---|---|
| `nl2query` | question → LogforgeQL | 1 if it compiles to the same request as the reference (filters, aggregations, grouping order-insensitive; relative windows compared by length), else 0 |
| `summaries` | evidence `{E1: ...}` → summary citing `[E1]` | required-fact coverage (0–1), but **0 if any sentence is uncited or cites evidence that doesn't exist** |
| `rule_drafting` | behaviour description → Sigma YAML with fixtures | 1 if the draft passes the platform's fixture gate, detects the item's attack events, and raises nothing on the benign corpus from `tests/eval/detection` |

```bash
python tests/eval/ai/ai_eval.py    # scores the reference answers (all 1.0)
```

```python
import ai_eval
result = ai_eval.evaluate("nl2query", my_feature)   # my_feature(item) -> str
print(result["score"], result["per_item"])
```

## Features and the CI gate (Phase 8)

`run_ai_eval.py` runs the AI features in `apps/api/ai/features.py` against
these datasets through any provider:

| Feature | Dataset | What it does |
|---|---|---|
| `nl2query` | `nl2query` | question → one LogforgeQL query; an answer that doesn't compile counts as none |
| `summaries` | `summaries` | evidence → a two-to-four sentence summary citing `[E#]` |

CI runs them from **recordings** of a real model (`recordings/<feature>.jsonl`,
replayed by `ai.providers.recorded.RecordedProvider`, so no network or cost),
and `tests/test_ai_eval_gate.py` fails if a feature scores below its entry in
`baseline.json`. A recording is keyed by a hash of the whole request (model,
prompt, messages, tools): change a prompt and the old answers no longer
match, so the gate fails until the feature is re-recorded.

```bash
# record (calls the model once per item) and look at the scores
ANTHROPIC_API_KEY=... python tests/eval/ai/run_ai_eval.py --record --provider anthropic:claude-opus-5-5
# make them the baseline CI holds the feature to
python tests/eval/ai/run_ai_eval.py --update-baseline
```

`--provider` also takes a provider name from `config/ai.yml`, or
`ollama:<model>@<url>` / `openai_compatible:<model>@<url>` for a local model.

**Not yet gated:** no recordings are committed yet (they need a model API
key), so both features are reported as skipped by the gate. The harness,
recorder and gate are tested end to end with a scripted stand-in.

## Natural language to LogforgeQL: execution accuracy (Phase 9)

Three sets of question/query pairs, one per schema, generated by
`nl2query_dataset.py` from templates over the Phase 6 seeded week of events:

| Set | Items | Covers |
|---|---|---|
| `datasets/nl2query_auth.jsonl` | 242 | auth and VPN sign-ins: outcome, user, source IP, country, host |
| `datasets/nl2query_http.jsonl` | 214 | web and API requests: status, method, path, duration, bytes, user agent |
| `datasets/nl2query_dns.jsonl` | 205 | DNS queries: domain, host, user |

`tests/test_nl2query_eval_live.py` seeds the events into ClickHouse and runs
each generated query: it is right when it returns the same rows as the
expected query (`nl2query_exec.py`). Every expected query returns rows.

| System | auth | http | dns |
|---|---|---|---|
| Rule-based fallback (AI off) | 0.4% | 9.8% | 11.2% |
| Model (`ai.nl2query.translate`) | not recorded | not recorded | not recorded |

The target for the model is ≥ 85%. The rule-based fallback has no idea of a
schema's fields (it can't know that a sign-in is `attrs.outcome` in the
`auth` and `vpn` services), so it handles only questions naming a level, a
service, a seen value or a column. Record and score a model with
`record_nl2query_exec.py --provider ... --update-baseline`; both scores are
then held as regression floors (`baseline_nl2query_exec.json`).

Limitation: templated questions are more regular than an analyst's.

## Alert and case triage summaries (Phase 9)

`datasets/triage.jsonl` (written by `triage_dataset.py`) has 20 items: 16
alerts across ATT&CK tactics (and one with no technique), and 4 cases of two
alerts each. Each carries the evidence a summary is built from: the alert or
case, the related activity of its entities and threat intelligence matches,
plus the facts a summary must state (title, entities, techniques, intel
sources). `tests/test_ai_triage_eval.py` scores, per `triage_eval.py`:

| System | Items | Uncited sentences | Raw uncited rate | Fact coverage |
|---|---|---|---|---|
| Template (AI off) | 20 | 0 | 0% | 100% |
| Model (`ai.triage.write`) | 20 | 0 by construction | not recorded | not recorded |

The target is zero uncited claims. The product drops any sentence a model
writes without a valid citation (`dropped`), so a summary never shows one;
the raw uncited rate measures how often a model needed that. The template
cites every sentence by construction. Its full fact coverage is expected:
the required facts are the ones the evidence holds, and the template states
all of them. It says less than a model could (nothing about why the events
matter beyond the tactic). Record a model with
`record_triage.py --provider ... --update-baseline`.

## Pipeline drafts from sample logs (Phase 9)

Held-out formats: the content packs' 14 sample files (85 lines: CloudTrail,
VPC flow logs, Okta, Google Workspace, Kubernetes audit and container logs,
auth.log, auditd, syslog, nginx and Apache access and error logs, Windows
Security and Sysmon). The drafter gets the raw lines and the service name,
never the packs' pipelines. `tests/test_ai_pipeline_draft_eval.py` scores, per
`pipeline_draft_eval.py`:

* parse rate: lines the draft parses in simulation;
* value recall: field values the pack's own expectations name that appear
  literally in the raw line (58 of them), found among the values the draft
  extracted, whatever it named the field.

| Drafter | Files | Lines | Parse rate | Value recall |
|---|---|---|---|---|
| Heuristic (AI off) | 14 | 85 | 100% | 91.4% |
| Model (`ai.pipeline_draft.draft`) | 14 | 85 | not recorded | not recorded |

The heuristic misses values inside free-text messages (the user in an sshd
line, the request in an nginx error line): it splits a syslog header and
key=value pairs but doesn't write a regex for prose. The packs were written
before the drafter, but the drafter was developed with these files in view,
so they are held out from the drafting, not from its author. Record a model
with `record_pipeline_draft.py --provider ... --update-baseline`.

## Explain this event (Phase 9)

The content packs' sample files, parsed by the packs' own pipelines (as
pack CI does), give 83 events; each sample also lists the rules its events
must fire (28). `tests/test_ai_explain_eval.py` scores, per `explain_eval.py`:

| System | Events | Uncited sentences | Identified | Rule recall |
|---|---|---|---|---|
| Template (AI off) | 83 | 0 | 90.4% | 100% |
| Model (`ai.explain.write`) | 83 | 0 by construction | not recorded | — |

"Identified" means the explanation says what the event is from a reference
entry (Windows or Sysmon event ID, auditd record type, a known message,
HTTP status, OCSF class) rather than "an event from <service>". The misses
are application lines (a Kubernetes container's own messages, a Postgres
checkpoint, an nginx buffering notice), where a model adds the most. The
reference entries were extended while looking at these events (a Sysmon
mix-up, auditd types, cron, systemd and two nginx errors), so this set is
not held out from the reference's author. Rule recall comes from matching
the event against the shipped library with the detection engine's matcher.
Record a model with `record_explain.py --provider ...`.

## Investigation copilot (Phase 10)

`datasets/copilot_scenarios.jsonl` (written by `copilot_scenarios.py`) has 20
scenarios, ten kinds in two variants: SSH brute force then an account,
then persistence; a web shell; credential dumping; RDP brute force then
shadow copies deleted; starting from an attacker's address; starting from
an account the attacker created (the root cause is found only by
pivoting); log clearing; a reverse shell from a web request; a phishing
download. Each has background activity (cron, routine logins, a mistyped
password, sudo, web traffic, Windows logons) and its root-cause event
marked. Variant 1 of two kinds adds a benign admin action with the same
signal as the attack inside the window before it.

`tests/test_copilot_eval_live.py` seeds them into ClickHouse (one tenant
each) and runs the copilot as an analyst who approves what it proposes
once: plan, run, then run again with its next steps (`copilot_eval.py`).

| System | Scenarios | Root cause found (in candidates) | Found first | Fabricated evidence |
|---|---|---|---|---|
| Template (AI off) | 20 | 90% | 80% | 0 |
| Model (`ai.copilot.write`) | 20 | not recorded | not recorded | 0 by construction |

The target is >= 80% found with no fabricated evidence. The misses: both
phishing downloads (the download carries no signal the copilot knows; it
names the payload running instead). The benign admin action ranks first in
both distractor variants, with the real root cause second. The scenarios
were written alongside the copilot's signals, so they test the method, not
how it does on unseen attacks. Record a model with
`record_copilot.py --provider ... --update-baseline`.

## Detection drafting (Phase 10)

`datasets/rule_behaviours.jsonl` (written by `rule_behaviours.py`) has 20
behaviours across 17 ATT&CK techniques: shadow copies deleted, LSASS dumps
(ProcDump, comsvcs, Mimikatz), log clearing, encoded PowerShell, local admin
added, Linux accounts, reverse shells, downloads to /tmp, SSH keys added,
cron and scheduled-task persistence, certutil downloads, dynamic-DNS
lookups, web shells, SQL injection, Defender switched off, Kerberoasting,
privilege discovery. The drafter gets the description, the technique, the
attack samples and one known-good event; held-out attack and benign events
check that the rule generalises and stays quiet (`rule_draft_eval.py`).

| Drafter | Behaviours | Passed within 2 attempts | First attempt | Held-out recall | Held-out quiet |
|---|---|---|---|---|---|
| Heuristic (AI off) | 20 | 90% | 90% | 88.9% | 100% |
| Model (`ai.rule_draft.draft`) | 20 | not recorded | not recorded | — | — |

"Passed" means the Phase 1 fixture gate accepted the draft (its own
fixtures, the benign corpus, a technique tag), it fires on every attack
sample and not on the known-good event. The target is >= 70%; nothing is
enabled without passing, because enabling (`/v1/ai/rule-draft/enable`) runs
the gate, the samples and a backtest again (`tests/test_ai_api.py`). The
heuristic fails encoded PowerShell and `whoami /priv`: what the attack
samples share is in the known-good event too. Of the drafts that pass, two
miss their held-out variant (a different MiniDump invocation, `UNION ALL`).
The behaviours were written alongside the drafter. Record a model with
`record_rule_draft.py --provider ... --update-baseline`.

## Status

This is the Phase 0 skeleton: scorers, small seed datasets (8 / 5 / 5 items)
and tests (`tests/test_ai_eval_harness.py`) proving that a perfect system
scores 1.0 and a null system 0. Next:

- grow each dataset (Phase 9 targets ≥ 200 `nl2query` items per schema);
- execution accuracy for `nl2query` against a seeded stack, alongside the
  offline equivalence check;
- score the current rule-based NLQ (`apps/api/services/nlq_processor.py`) as
  the no-AI baseline once it can emit LogforgeQL.
